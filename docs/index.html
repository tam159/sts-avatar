Decoupled Speech-to-Speech (STS) AI Avatar Architecture

A BYO-Brain (Bring Your Own Brain) design decoupling real-time audio models from avatar renderers for multi-language interactive digital human applications.

1. End-to-End Architecture

Step 1: Client

Browser / Mobile

Captures user microphone stream via WebRTC

Step 2: Orchestration

LiveKit Framework

Bi-directional WebRTC room & agent dispatcher

Step 3: STS Brain

Gemini Live / OpenAI

Direct Audio-In to Audio-Out model processing

Step 4: Avatar Engine

Simli / LemonSlice / Tavus

Receives audio stream, renders lip-sync video back to LiveKit

Key Decoupling Benefit: The video rendering engine and the intelligence layer are strictly separated. You can seamlessly swap the STS model (e.g., from Gemini to OpenAI) by updating 1 line of backend configuration without impacting the WebRTC video streaming pipeline.

4. Infrastructure Strategy: LiveKit Deployment in Japan

LiveKit Cloud vs Self-Host Decision Matrix

Option A: LiveKit Cloud (Recommended for Launch)

  • ✓ Dedicated edge nodes in Tokyo (ap-northeast-1).
  • ✓ Sub-15ms round-trip latency inside Japan.
  • ✓ Zero DevOps burden for TURN/STUN scaling & WebRTC UDP routing.
  • ✓ Free tier included; scale-as-you-go pricing.

Option B: Self-Host on K8s (AWS EKS / GCP GKE Tokyo)

  • ✓ Complete data privacy & compliance control inside Japanese region.
  • ✓ Cost efficiency at massive scale (>10,000 concurrent streaming hours/month).
  • ✗ Requires managing complex WebRTC UDP ingress & Coturn infrastructure.

Kubernetes Architecture for Self-Hosted Deployment

If self-hosting on EKS (Tokyo - `ap-northeast-1`), your Kubernetes cluster requires the following containers/services:

livekit-server (Pod)

Core SFU handling audio/video WebRTC routing. Requires NodePort / HostNetworking for UDP ports (e.g., 50000-60000).

livekit-agent-worker (Pod)

Python worker running LiveKit Agents framework. Holds the WebRTC session to STS model (Gemini/OpenAI) and pipes audio to Simli/LemonSlice.

Redis Cluster

Distributed state management for room assignment, node discovery, and agent worker routing.

Coturn (TURN/STUN)

Traverses strict enterprise NAT/firewalls in Japanese corporate networks over TLS (port 443).

AWS Network Load Balancer

Layer 4 NLB preserving client source IP addresses with TCP/UDP listener support.

Cert-Manager & ExternalDNS

Automates SSL certificates and DNS routing for secure WebRTC wss:// connections.

5. Knowledge Base Setup: Ingestion & Retrieval

The MVP must answer questions about the company using approved company documentation, including its overview, products, services, and FAQs. Choose the retrieval approach based on the size and complexity of the knowledge base (KB).

Shared Document Ingestion Pipeline

Both approaches need a repeatable pipeline: collect source documents → extract text (OCR when needed) → clean and deduplicate → organize content with source references and update timestamps → review → publish a versioned KB.

Track source changes and deletions so published knowledge stays current. Preserve document identity and provenance through ingestion, and prepare a representative set of company questions with expected answers to evaluate retrieval.

Small KB: OKF Pages + Progressive Disclosure

Store a few curated company pages in Open Knowledge Format (OKF): Markdown files with YAML frontmatter and links between related pages. An index.md provides the entry point.

  1. Ingest: Convert approved documents into topic pages such as company overview, products, and FAQs; generate an index with short descriptions and page paths.
  2. Retrieve: Feed only the index into the AI's context initially. On a company question, the AI calls read_kb_page(path) to fetch relevant pages and follows links only when more detail is needed.
  3. Maintain: Republish changed pages and refresh the index when topics change. No embedding model or vector index is required.

Best when the index is compact and topics are easy to navigate. Progressive disclosure limits initial context, but multiple page reads can add voice-response latency.

Large KB: Semantic Search with Embeddings

  1. Ingest: Split normalized documents into meaningful chunks, retain source metadata, generate embeddings with a model evaluated for English, Japanese, and Vietnamese, and store vectors in a searchable index.
  2. Retrieve: The AI calls search_kb(query). Embed the query with the same embedding model/version as the indexed chunks, search for relevant passages, and return a bounded set of excerpts with source references.
  3. Maintain: Re-embed changed or new chunks and remove deleted content. Changing the embedding model requires rebuilding the vector index; changes to chunking can also require reprocessing and re-embedding.

More ingestion and operational complexity, plus embedding and index costs. In the next phase, add full-text search and combine keyword and semantic results for hybrid retrieval, especially for exact product names and identifiers.

Connect Retrieval to the STS Conversation

Expose the selected retrieval tools through Gemini's function calling or GPT-Live's delegated backend. The backend reads pages or searches the index and returns grounded content for the spoken answer. Keep retrieved content within a context budget and retain source references in the transcript. If the KB does not contain an answer, the AI should say so and offer a company contact instead of inventing facts.

Architectural Recommendation Summary

For initial deployment targeted at Japan supporting English, Japanese, and Vietnamese:

  1. Orchestrator: Use LiveKit Cloud (Tokyo Region) to bypass WebRTC infrastructure complexity during MVP phase.
  2. STS Brain: Evaluate Gemini 3.8 Live for multimodal input and usage-based audio pricing, and OpenAI GPT-Live 1 for full-duplex voice with delegated backend tools. Select the primary and fallback after measuring language quality, latency, and total session cost.
  3. Avatar Engine: Experiment with Simli, LemonSlice, and Tavus during weeks 1–2, then select the provider based on integration feasibility, lip-sync quality, latency, and cost.
  4. Company Knowledge: Build a document ingestion pipeline for either approach. Start with OKF pages and progressive disclosure for a small KB; use semantic retrieval with embeddings for a large KB, including re-embedding on content changes. Connect retrieval through STS tool calling; consider full-text/hybrid search in the next phase.
  5. Delivery: Plan a 5-week MVP: 2 weeks of provider experiments and selection, 2 weeks of KB ingestion and retrieval integration, and 1 week of end-to-end testing and QA.
